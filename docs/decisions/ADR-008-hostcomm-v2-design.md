# ADR-008：由项目定义 HostComm 2.0 固件开发契约

## 状态与日期

接受为开发设计基线，2026-09-06。用户确认目标 STM32 固件尚未开发，并授权设计通信契约。
协议设计、上位机适配、固件实现、真机验收是四个独立状态；本决策不表示后三者完成。

本决策替代 [ADR-006](ADR-006-candidate-experiment-contracts.md) 中“等待外部固件定义新增契约”的前提。
ADR-006 继续解释当前 `0.3.0-rc.2` 的 HostComm 1.0 行为；[ADR-007](ADR-007-device-gateway-lease.md) 的同机网关锁继续保留，不能代替本决策要求的板端控制租约。

## 问题

现有 JSON Lines 协议适合作为起点，但不能直接冻结给新固件：

- 现有配方允许最多 64 阶段；实际可通过当前 Mock 范围校验的 32 阶段报文也会超过 8192 字节帧上限。
- Python 排序 JSON 中 `1` 和 `1.0` 产生不同摘要，尚无跨 C/Python/浏览器的数值字节规范。
- 操作记录和网关锁在上位机，不能保证第二台上位机或板端重启后不会重复执行。
- 当前 Mock 的状态查询会分配采样序号；首个收到的终态快照也不能准确代表断线期间的测定边界。
- 现有软件没有设备日志分块补传和经过认证的板端传输实现。

## 决策

1. 新固件以 [HostComm 2.0](../hostcomm/v2/README.md) 为开发目标。保留 TCP、UTF-8 JSON Lines 和 8 KiB 单帧界限；配方采用有界分块上传。安全传输、身份、帧校验、操作和执行状态各自有明确边界。
2. 使用新的主版本，因为字段类型、配方摘要、终态和操作协议改变。现有运行代码及安装包仍使用 1.0；本次不在原解析器上悄悄改变语义。迁移通过独立适配器、类型和故障测试完成；生产连接不得自动降级并获得控制权。
3. 工程量使用具名固定点整数，64 位计数器使用规范十进制字符串。配方限定为 RFC 8785 可实现的整数子集，对完整规范 UTF-8 字节作 SHA-256。旧 CRC32 仅保留在 1.0 适配器，不能把算法名相同当作数据等同。
4. 板端持有控制租约、掉电保存的操作序号高水位、运行身份和边界日志。先持久化意图再受理；无法确定的物理结果保留 unknown，不承诺断电条件下的物理“恰好一次”。结果缓存淘汰后仍不能再次执行旧序号。
5. 实时阶段、安全处置、首滴事件和原始采样身份由板端产生。安全处置独立于用户配方，非标配方不能删除置换、撤 CO、联锁或安全冷却；通信丢失按批准的设备安全配置退出测定，不因重连自动恢复。
6. 使用有界、可校验、可报告缺口的日志补传。历史补传只修复归档，不驱动实时控制。板卡容量通过能力声明，存储不足时明确限制启用条件，不能假装具有无限离线缓存。
7. 当前代码、Mock、2.0 设计与未来固件分别标记。电气联锁时序、传感器范围、气体标态和标准原文冲突仍需工程/试验证据；不以协议设计替代批准。

## 备选与取舍

继续堆叠 1.0 可选能力会保留浮点摘要、模糊终态和身份歧义，因此只保留其兼容说明。扩大单帧会增加 MCU 内存压力，也不能解决原子激活。二进制协议可以降低带宽，但首期以有界 JSON 方便抓包、跨语言检查和维护；固定点整数与分块控制其成本。

传输认证采用标准 TLS，避免自创逐报文鉴权算法。板型尚未选定，因此 TLS、存储和任务调度的资源验收必须进入选型阶段；做不到时调整硬件或经新 ADR 修改设计，不能以关闭认证获得“兼容”。

## 验证和实施

机器契约、报文和摘要向量位于 [contracts/hostcomm/v2](../../contracts/hostcomm/v2/README.md)，状态及故障规则见[状态与恢复](../hostcomm/v2/state-and-recovery.md)。自动检查只证明结构、字节规范和所列参考行为，不能证明板端控制、安全或耐久性。

按[固件与上位机实施顺序](../hostcomm/v2/firmware-plan.md)推进。正式互操作验收必须绑定协议契约修订、上位机 SHA、固件 SHA、板卡/仪表/配置版本，并完成丢回执、重启、存储故障及实际联锁测试。
