# 发布与维护指南

维护角色：发布负责人。当前实现核查基线 `dev@855c84d`；本文明确区分现有源码部署和目标桌面交付。选择依据见 [ADR-003](decisions/ADR-003-project-baseline.md)、[ADR-005](decisions/ADR-005-shared-runtime-and-evidence.md)。

## 1. 分支和版本

`main` 是整合后的唯一长期分支；功能/修复从当前主线建立短期分支，经 PR 和必要 CI 后 squash 合并并删除。此次 dev 历史整合保留祖先关系，属于 ADR-003 的一次性例外。既有主线历史和发布标签保持原样，清理前的 Git bundle/引用清单保存在仓库外并验证可恢复。

版本真源为 `backend/app/__init__.py` 的 `__version__`；前端 package.json/lock、包清单和 tag 必须与该版本一致。使用 SemVer，候选版使用 `0.3.0-rc.N`，tag 使用 `v` 前缀。已发布的 tag 不移动；修复发布新版本。维护 CHANGELOG，说明用户可见变化、兼容范围、迁移和回滚限制。

配置主线 PR、必要 checks 和合并后自动删分支；无法因 GitHub 套餐/权限启用保护时记录限制，不声称已被平台强制执行。禁止以正式 tag 绕过未完成的检查。

## 2. 软件与发布检查

PR 和 tag 发布应调用同一套必要检查：文档/链接、格式、后端测试及覆盖率≥80%、前端 lint/测试/构建、契约与类型、依赖审计。桌面交付加入离线包校验、Windows 安装/服务/升级/回滚。版本一致性检查和所有必要检查均通过后才允许创建发布产物。

基线已有 Linux/Windows 后端测试、前端检查、哈希锁文件和阻断式依赖审计；tag构建与完整检查尚未统一，不能把“已有CI”写成“所有发布门禁完成”。目标运行时为 Node 24 LTS、Python 3.13；Python3.11继续验证旧基线迁移，实际支持组合以CI/Windows证据为准。

每份包附带：应用版本、提交SHA、构建环境、依赖/组件清单、文件SHA-256、数据库迁移版本、协议/固件能力范围、变更说明、安装与恢复说明。校验值用于完整性，正式分发还须有可信来源/签名证据，不能将同包中的hash当成身份认证。

RC标记为预发布；Windows或真实固件未通过的项目在发行说明中列明。M5未验收不得宣称完整国标或正式现场适用。

## 3. 当前 Windows 脚本基线

现有 [Windows说明](../deploy/windows/README.md)对应源码+wheels ZIP，需要用户预装Python3.11，以SYSTEM计划任务运行。它还不是独立exe桌面安装器。

已知升级缺口：原地修改venv后回滚只恢复app/db；脚本硬编码默认数据库位置；后台启动后未充分等待就绪；部署根脚本和环境不能整体回退。这些问题由M4替换，不将旧脚本列作生产升级验收证据。现有实验数据应按实际配置定位和备份，不能默认只有安装目录下data/smd.db。

## 4. 目标双端安装

Win10/11 x64使用pywebview薄壳、固定WebView2 Runtime、PyInstaller onedir、NSIS安装器和独立Windows Service。安装包包含运行环境，干净断网主机不需预装Python/Node。桌面普通用户启动；后台使用受限服务身份；安装、服务注册、证书和目录ACL由管理员配置。

程序和运行环境存入版本目录；数据、配置、日志、报告、备份和升级事务存入ProgramData。后台单实例、单设备网关，桌面多开只产生界面；关闭窗口、退出登录不结束实验。卸载默认保留实验数据。

桌面和浏览器共享UI、API与认证。局域网使用HTTPS/WSS和现场信任的证书，明确访问范围和防火墙规则；不把关闭证书校验作为运行方式。签名密钥和证书私钥不随源码或公开包分发。

固定WebView2版本在组件清单标明，运行时安全更新随人工离线包发布。安装验收覆盖中文/空格路径、普通用户、重启自启、报告下载、窗口缩放及版本不匹配页面。

## 5. 人工离线升级事务

目标升级顺序固定为：

1. 验证包来源、签名/校验、平台、应用/数据库/协议兼容性，完整暂存新程序与运行环境。
2. 获取持久维护锁；确认无进行中实验、无待决控制操作且设备处于允许维护状态。已有实验时拒绝切换，不能强停实验完成升级。
3. 停止后台及自动重启机制，按**旧配置解析后的实际路径**备份数据库、配置、证书引用和版本指针；执行SQLite完整性验证并记录校验值。
4. 使用新运行环境对保留的数据执行迁移；完整记录开始、阶段、旧/新版本、备份位置和错误。
5. 切换版本指针，启动受限服务，在有界超时内验证应用存活、数据库/schema、可写存储、后台唯一实例、静态页面和认证接口。
6. 验活通过才提交事务并释放维护锁；失败恢复旧程序、依赖环境、配置、数据库和版本指针，重新验活，保留失败证据。

断电后根据持久事务阶段恢复，不凭目录名字推测成功。数据库迁移尚未提交的失败回滚与运行一段时间后的人工降级不同：后者必须先保留新版本期间数据并评估兼容，不能用旧备份直接覆盖后来实验。回滚依赖完整环境，不使用未经验证的Alembic downgrade替代。

应用就绪与设备就绪分别判断：设备离线不阻止首次安装或历史查询；它会阻止需要可靠设备状态的控制操作。已连接但状态过期也不构成可控制。

## 6. 日常维护与证据

按实际配置管理数据库、报告及备份；定期校验备份并在隔离环境演练恢复。原始实验长期保留策略由现场规定，自动清理仅覆盖明确的滚动缓存和临时导出，不能清理实验原始记录。

记录磁盘余量、备份最近成功时间、写入故障、队列深度/年龄、丢弃/缺口计数、设备/WS连接和数据新鲜度。控制请求失败和结果未知单独统计，避免恢复网络后自动补发动作。

每次升级保留主机OS版本、安装包hash、前后版本、数据库版本、服务身份、迁移日志、验证结果和恢复演练记录。按冻结的最高采样频率至少运行24小时，检查内存、队列、存储和命令响应。软件、模拟器、Windows和真机证据按[验证规范](verification.md)分别归档。
